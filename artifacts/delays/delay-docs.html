Opóźnienia ZTM: dokumentacja

Jak serwer szacuje opóźnienie autobusu lub tramwaju na żywo, gdzie to widać w aplikacji, jak z tego korzystać przy pracy nad UI i czego jeszcze brakuje. Liczby są na artifacts/delays/delay-statistics.html, a co i na czym testowałem: artifacts/delays/tests/delay-tests.html.

W skrócie

  • Lista proponowanych tras: przy każdym autobusie i tramwaju widać jego opóźnienie na żywo, np. „180 · 12′ · +3 min”. Działa dla każdej linii autobusowej i tramwajowej.
  • Pojazd, w którym jedziesz (po „Jadę tą linią”): opóźnienie przychodzi co 10 s w evencie bus-delay, ale żaden element ekranu go jeszcze nie pokazuje.
  • Dokładność na 32 min prawdziwych danych: opóźnienie dostępne dla 98,2% przejazdów, połowa wyników różni się od wzorca o 2 s lub mniej.

Jak to działa na serwerze

  1. Pozycje na żywo. Serwer co 3 s pobiera pozycje wszystkich autobusów i tramwajów z API Urzędu Miasta (feed zmienia się mniej więcej co 10 s). Każdy wpis ma linię, brygadę, numer taborowy, współrzędne i czas.
  2. Bufor pojazdu. Dla każdego pojazdu serwer trzyma pozycje z ostatnich minut: najdłuższy planowy przejazd między dwoma przystankami jego kursu + 60 s (10 min, gdy kursu nie da się ustalić). Między dwoma odczytami dopisuje punkt w połowie drogi, więc pozycja jest mniej więcej co 5 s. Nie dopisuje go, gdy pobranie się nie udało albo odczyty dzieli więcej niż 25 s.
  3. Kurs z rozkładu. Linia + brygada wskazują kursy z rozkładu GTFS. Serwer rzutuje pozycję na trasę każdego kursu, który jedzie teraz ± 15 min i przebiega bliżej niż 100 m, i wybiera ten, którego rozkład w tym miejscu trasy jest najbliżej „teraz” (brygada jeździ tą samą trasą kilka razy dziennie).
  4. Ostatni minięty przystanek (K-1) to ostatni przystanek kursu przed miejscem, w którym jest pojazd. Następny to K.
  5. Moment przejazdu: punkt z bufora najbliższy przystankowi K-1, ale tylko w promieniu R = 30 m (DELAY_RADIUS_M). Brak takiego punktu = „dane o opóźnieniu niedostępne”.
  6. Opóźnienie = moment przejazdu − planowy odjazd z K-1. Może być ujemne (przed czasem). Pokazujemy je jako przewidywane opóźnienie na następnym przystanku K.

Lista proponowanych tras

  1. Po wyszukaniu trasy useRouteDelays (w RouteOptionsSheet) wysyła listę propozycji do POST /api/live/route-delays: raz po pojawieniu się listy, potem co 30 s, dopóki lista jest na ekranie.
  2. Serwer odczytuje kursy z identyfikatora propozycji (pt-<kurs>-<kurs>), z każdego kursu bierze linię i brygadę i w danych na żywo znajduje pojazd z tą samą linią i brygadą. To ten konkretny autobus, który przyjedzie.
  3. Dla tego pojazdu liczy opóźnienie jak wyżej. Gdy pojazd jeszcze kończy wcześniejszy kurs swojej brygady (np. jedzie do pętli), oddaje jego obecne opóźnienie jako prognozę (sameTrip: false).
  4. LegChain dopisuje opóźnienie za linią i czasem jazdy. Etykieta silnika „opóźnienie N min” jest wtedy ukryta, żeby na karcie nie było dwóch różnych liczb.

Powody „niedostępne” (reason): no_trip (brak kursu w rozkładzie), outside_trip (pojazd na pętli), no_pass_in_radius (brak pozycji blisko ostatniego przystanku), no_vehicle (brak pojazdu tej brygady na żywo), not_live (metro, pociąg, nieznany kurs).

Event bus-delay dla pracy nad UI

Po kliknięciu „Jadę tą linią” useVehicleDetection uruchamia watchDelay z src/api/delay.ts: co 10 s pyta GET /api/live/delay i wysyła na window event bus-delay z odpowiedzią w event.detail (typ BusDelayDetail w src/types.ts). Polling kończy się przy nowej detekcji i po „Nie jadę komunikacją”. Gdy serwer nie zna pojazdu (404, np. linia wybrana ręcznie), reason to unknown_vehicle; gdy nie odpowiada, backend_unavailable.

gotowy hook: src/hooks/useBusDelay.ts
import { useEffect, useState } from 'react';
import { BUS_DELAY_EVENT } from '../api/delay';
import type { BusDelayDetail } from '../types';

/** The latest `bus-delay` answer for the confirmed vehicle, or null before the first one. */
export function useBusDelay(): BusDelayDetail | null {
  const [delay, setDelay] = useState<BusDelayDetail | null>(null);
  useEffect(() => {
    const onDelay = (e: Event) => setDelay((e as CustomEvent<BusDelayDetail>).detail);
    window.addEventListener(BUS_DELAY_EVENT, onDelay);
    return () => window.removeEventListener(BUS_DELAY_EVENT, onDelay);
  }, []);
  return delay;
}

Przy wyświetlaniu warto użyć istniejących funkcji z listy tras, żeby napisy były takie same: legDelayLabel i legDelayKind w src/api/routeDelays.ts (po przekształceniu delaySec na LegDelay). Sprawdzaj delay.vehicleId === confirmed.id, bo po zmianie pojazdu może jeszcze dojść ostatni event poprzedniego.

Jak uruchomić i sprawdzić

  • Serwer: cd backend && uv run uvicorn main:app (potrzebny PORTAL_KEY w .env). Pierwsze minuty po starcie: bufor się zapełnia, odpowiedzi 503 albo no_pass_in_radius.
  • Jeden pojazd: curl "localhost:8000/api/live/delay?vehicle=bus-5914" (id z okna „W jakim pojeździe jestem”).
  • Testy: cd backend && uv run pytest tests ../algorithms; frontend: npm run lint, npm test, npm run build.
  • Statystyki od nowa z nagrania: uv run python ../algorithms/simulation/export_delay_viz.py; najlepszy promień: search_delay_radius.py; nowe nagranie (serwer włączony, 30 min): record_delay_sample.py 30.

Ograniczenia i do zrobienia

  • Przejście na RouteLeg.tripId. Lista tras bierze kursy z identyfikatora propozycji. Szymon prosi o czytanie ich z nowego pola tripId odcinka (już na main, PR #93). Dziś działa poprawnie; chodzi o odporność na zmiany w silniku.
  • Zawijanie napisu. Dłuższy napis („ok. 1 min wcześniej”) łamie się w dwie linie i rozbija napis linii na karcie. Do poprawki w LegChain.tsx (np. white-space: nowrap na napisie odcinka).
  • Brak widoku dla pojazdu, w którym jedziesz: dane płyną w evencie bus-delay, nikt ich jeszcze nie pokazuje.
  • Trasy z przystankami pośrednimi (identyfikator multi-N), metro i pociągi nie mają opóźnień.
  • Opóźnienie zmienia się skokowo, gdy pojazd minie kolejny przystanek (co 1–3 minuty).
  • Router C++ nie buduje się na Windowsie (kod używa pwrite), więc na takim komputerze nie zadziała pełne wyszukiwanie trasy komunikacją.
